# FastRelease

给「dev 开发 → release 上线」这套 cherry-pick 流程用的桌面小工具。

三个页签，对应三种用法：

| 页签 | 干什么 |
|---|---|
| **快速合并** | 左右两栏各放一个分支，勾选左边几个提交，一次摘取到右边，再一键推送 |
| **合并检查** | 按人 / 时间查「dev 上哪些提交还没进 release」，用于上线前核对 |
| **代码修复快速合并** | 一次把同一批修复提交摘到多个分支（release-1 / release-2 / hotfix…） |

界面和交互参照 TortoiseGit：浅色、紧凑、工具栏 + 列表；冲突解决参照 TortoiseGitMerge 的三栏对照。

---

## 快速开始

- 双击目录里的 **`FastRelease.bat`**（推荐，无控制台窗口）
- 或命令行 `npm start`
- 新机器第一次用：先 `npm install`

启动后会记住上次打开的仓库和上次选的分支。

## 功能说明

### 一、快速合并

- 左右两栏各自选分支（本地 / 远端都能选），支持按提交信息、作者、时间筛选，分页加载
- 勾选提交 → 「摘取」或「摘取并推送」
- 执行时会自动切到目标分支

**「已摘取」徽标**：标记该提交是否已存在于对侧分支，判定分三层（见下文）。

**工作区改动**：顶部「工作区 N 处改动」可以看未提交改动的 diff（按行高亮），摘取前后自动处理暂存，详见下文。

### 二、合并检查

选源分支、目标分支、检测人、时间范围，列出还没合并过去的提交：

| 状态 | 含义 |
|---|---|
| 已合并 | 目标分支存在等价补丁（patch-id 一致） |
| 已合并·squash | 目标分支文件内容一致，或三方合并无残留 |
| 可能已合并 | 目标分支上同一处被后续改过，无法自动判定，建议人工看一眼 |
| 未合并 | 确实没有这段改动 |

支持「只看未合并」，双击某行可以看提交详情。

### 三、代码修复快速合并

左栏照旧选提交，右栏改成**本地分支多选列表**：

- 点「摘取」/「摘取并推送」，会按列表顺序逐个分支执行
- 执行前先逐分支判定：这批提交里哪些已经在该分支上，自动剔除；一个都不剩的分支直接跳过（确认框里会写明）
- 某个分支遇到冲突会停下来，用内置冲突界面解决，解决完**自动继续下一个分支**；点「中止」则停掉剩余分支
- 摘取并推送：每个分支摘完立刻推送，某个分支推送失败只记录，不影响其它分支
- 右栏底部会显示每个分支的结果（已摘取 / 已合并跳过 / 失败 / 已中止）
- 源分支本身会置灰不可选（摘回自身必然冲突）

## 工作区改动与自动暂存

摘取 / 拉取前如果工作区有未提交改动，会先 `git stash push -u`（含未跟踪文件）暂存，操作完成后自动恢复。

- 恢复用 `git stash pop --index`，所以**「已暂存 / 未暂存」的区分会原样保留**
- 恢复时如果和操作后的文件内容冲突，会打开内置冲突界面让你逐块解决；点「放弃恢复」则回滚工作区，改动仍完整留在 stash 里
- 冲突还没解决就中途退出也没关系，改动会一直留在 stash，不会丢

## 「是否已合并」怎么判定的

squash 会把多条提交压成一条，原来提交的 patch 在目标分支上就不存在了，所以只比 patch 是不够的。这里分三层：

| 层 | 做法 | 成本 | 能解决什么 |
|---|---|---|---|
| ① patch-id | `git cherry` 同款比对 | 1 次管道 | 摘取、变基、rebase 后的常规场景 |
| ② 内容比对 | 提交改过的文件在目标分支上 blob 是否一致 | 固定 2 个进程，与提交数无关 | squash 后文件没再被改过 |
| ③ 三方合并干跑 | `git merge-tree --write-tree --merge-base=<C^> <target> <C>`，结果树是否等于目标树 | 较慢，只跑 ② 判不出的候选，带缓存 | squash 后文件在别处又被改过 |

**已知盲区**：squash 之后又在**紧邻位置**改过同一处时，git 的三方合并会算成同一个冲突块（即使值相同），这时会降级为「可能已合并」，需要人看一眼。这比硬判「已合并」（会漏摘）或硬判「未合并」（会重复摘）都安全。

git < 2.40 没有 `merge-tree --merge-base`，会自动只用前两层。

## 冲突解决

冲突窗口是三栏对照：左边当前分支内容，右边被摘取的提交（或你暂存的改动），中间是合并结果。

- 「用左侧 / 用右侧 / 两侧都保留」逐块选
- 保存并标记已解决 → 全部完成 → 继续摘取（批量模式下会接着跑下一个分支）
- 也可以「跳过此提交」或「中止并回滚」

## 打包成 exe

```
npm install     # 第一次
npm run dist    # 产物在 dist/
```

产物：

- `dist/FastRelease-<版本>-win64/FastRelease.exe` —— 直接双击运行
- `dist/FastRelease-<版本>-win64.zip` —— 整个运行目录的压缩包（约 113MB）

> 打包时会把 `packaging/README.md` 复制成包内的 `README.md`，那是给使用者看的说明；仓库根目录这份是开发者说明。

## 环境要求

- Windows + Git for Windows（`git` 需要在 PATH 里）
- Node.js 18+（仅首次 `npm install` 和打包时需要）

改代码后重启应用即可生效，不需要构建步骤。

## 目录结构

```
main.js             主进程：窗口、IPC 注册、配置读写
preload.js          contextBridge 暴露给渲染层的 api
src/git.js          所有 git 操作（提交列表、摘取、暂存、推送、已合并判定…）
renderer/
  index.html        三个页签的 DOM
  app.js            渲染层逻辑（Pane 类、批量队列、冲突界面…）
  styles.css        样式
scripts/pack.js     打包脚本
packaging/README.md 随包给使用者的说明
```

## 日志与排错

- 渲染层未捕获的异常会弹提示，同时写入日志：
  - 源码运行（`FastRelease.bat`）：`<仓库目录>/.data/renderer-error.log`
  - 打包版：`%APPDATA%\FastRelease\data\renderer-error.log`
- 配置也是分开放的：源码版在 `<仓库目录>/.data/config.json`，打包版在 `%APPDATA%\FastRelease\data\config.json`，两套互不影响
- 需要看 IPC 调用细节时，启动前设环境变量 `FR_IPC_LOG=1`

## 已知限制

- 批量页右栏只列**本地**分支（cherry-pick 必须先切到本地分支）；左栏可以选 `origin/dev` 这类远端分支作为源
- 合并检查的时间窗口默认封顶 90 天，避免大仓库上比对过慢
- 「可能已合并」需要人工确认，无法完全自动判定（原因见上文盲区）
